# 智慧养殖多智能体平台 — 硬件通信协议文档

- 文档版本：V1.3
- 依据文档：PRD V1.7 第 3.3 节（STM32 采集节点、模拟模式为"一等公民"）
- V1.3 变更（F09 实施回写，承接《17-功能PRD-F09》文档同步项⑤，待确认①已采纳）：第四节 confidence 分级补 death 事件升级注记（death confidence ≥0.5 即生成 high，其余四类维持 0.5~0.7 low / ≥0.7 mid）
- V1.2 变更（评审修复）：topic 中 device_id 明确为**设备序列号 device_sn**（device 表唯一字段），平台按 sn 回表校验归属，修复"字符串编号无法回表"缺口
- 适用对象：STM32 固件开发、模拟器开发、平台 MQTT 消费者开发
- **核心原则：在协议层模拟，不在功能层模拟。** 模拟器与真实 STM32 必须发完全相同的消息；本文档即模拟期定稿的通信契约。

## 一、连接与基础约定

| 项 | 约定 |
|----|------|
| Broker | EMQX（开发期 `localhost:1883`；演示期同机部署） |
| QoS | 1（至少一次）；消费端按 `msg_id` 去重 |
| Payload 编码 | UTF-8 JSON，单层为主，字段名 snake_case |
| 时间戳 | Unix 毫秒（`ts`），设备侧使用本地校时（NTP 或平台下发） |
| ClientId 规则 | `node_{device_id}`（STM32）/ `sim_{device_id}`（模拟器）/ `backend_consumer_01`（平台） |
| 认证 | V1.0 Broker 内网无鉴权；V1.1 启用 username/password + 每设备 ACL（只允许发布自己的 topic） |

## 二、Topic 命名规范

```
farm/{farm_id}/pen/{pen_id}/{device_id}/data       # 传感器数据上报
farm/{farm_id}/pen/{pen_id}/{device_id}/heartbeat  # 心跳（数据上报本身视为心跳，此 topic 供纯心跳场景）
farm/{farm_id}/pen/{pen_id}/{device_id}/event      # 视觉结构化事件（边缘网关/模拟器发布）
farm/{farm_id}/pen/{pen_id}/{device_id}/cmd        # 平台→设备 下行（V1.1 预留，暂不实现）
```

**规则**

1. topic 中的 ID 为**设备序列号 device_sn**（如 DEV001，device 表唯一字段，注册时分配；与 DB 自增主键 device_id 是两个字段），平台消费时按 sn 回表校验归属（topic 与库不一致 → 丢弃并记日志）
2. 设备只允许发布 `data / heartbeat / event`；订阅仅 `cmd`（预留）
3. 示例：`farm/1/pen/3/DEV001/data`

## 三、传感器数据上报 payload

### 3.1 上行（设备 → 平台）

```json
{
  "msg_id": "b7e2f0a1",
  "device_id": "DEV001",
  "ts": 1760000000000,
  "metrics": {
    "temperature": 27.8,
    "humidity": 71.5,
    "nh3": 12.3,
    "co2": 2100.0
  }
}
```

**字段说明**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| msg_id | string(16) | 是 | 消息去重 ID，设备侧用递增/随机，重发时保持不变 |
| device_id | string | 是 | 即 device 表的 device_sn（注册时分配，全局唯一） |
| ts | int64 | 是 | 采集时刻 Unix 毫秒 |
| metrics | object | 是 | 指标键固定四个：`temperature`(℃) `humidity`(%RH) `nh3`(ppm) `co2`(ppm)；本次未采集的指标可省略该键，但对象本身不可为空 |
| 数值 | float | - | 保留 1~2 位小数；异常传感器读数（负湿度等）由设备侧滤波剔除后不再上报 |

### 3.2 采集与滤波（STM32 节点侧要求）

| 项 | 规格 |
|----|------|
| 传感器 | 温湿度：DHT22 / SHT30（推荐 I2C）；NH₃：电化学模块（如 MQ-137 需标定，预算允许用 TGS 或电化学探头）；CO₂：MH-Z19（NDIR，UART） |
| 采集周期 | 默认 30 秒/次（可配置 10~300s） |
| 滤波 | 滑动窗口取中值（窗口 5 次）剔除毛刺；单点超量程丢弃 |
| 上报策略 | 每个采集周期上报一次滤波后值；网络断线时本地缓存最近 1 小时数据，恢复后补报（补报消息 ts 为原采集时刻） |
| 心跳 | 每次成功上报即视为心跳；若配置采集周期 >5 分钟，则额外每 60s 发一条 heartbeat |

### 3.3 平台侧处理

1. 按 `msg_id` 去重（Redis `mqtt:dedup:{msg_id}`，TTL 2h，覆盖 QoS1 重发与断网补报重放）
2. 校验 topic 归属与 JSON schema → 写 `sensor_data` 历史表
3. 更新 Redis `sensor:latest:{device_id}` 与 `device:hb:{device_id}`
4. 防抖判断：连续 3 次超 `species.env_threshold` → 生成告警（合并窗口 1 小时；warn 档=mid、critical 档=high）
5. 离线扫描任务：每分钟检查 `device:hb`，>5 分钟无心跳 → offline + device_offline 告警（V1.0 仅进告警中心，不触发 Agent）

**时序口径定稿（C-09，2026-10-16）**：历史行的 `ts` 用**消息时间戳**（补报要还原采集时刻），
心跳与在线状态用**服务端到达时间**。此前两者同用消息 ts，导致灌历史数据（Day1=2 天前）
被离线扫描秒判 offline 并多造一条 `device_offline` 告警——"补报"与"掉现"被同一根轴混用。
第 5 条的"每分钟"现已是真实后台任务（`main.py::_offline_scan_loop`，60s），
不再依赖"有人打开告警页"才判定；阈值可用 `OFFLINE_AFTER_SECONDS` 调整（演示默认 90s，真实口径 300s）。

**上行鉴权（C-24，2026-10-16）**：HTTP 入口 `POST /api/device/ingest` 双轨，两条都必须证明"这台设备归我"：

| 调用方 | 凭据 | 说明 |
|--------|------|------|
| 真实设备 | `X-Device-Key: <设备密钥>` | 建设备或 `POST /api/device/{id}/rotate-secret` 时**一次性**返回的明文，库内只存 sha256；密钥仅对那一台设备有效，轮换即失效 |
| 浏览器模拟器 | `Authorization: Bearer <农户 JWT>` | 且必须是该设备所在农场的主人（此前只验"是不是 farmer"，任何农户都能往别人圈舍写读数） |

两者都不带 → `40101`。MQTT 侧仍按第 1 节走 Broker 认证 + 每设备 ACL，与本表是并列的两条上行通道。

## 四、视觉结构化事件 payload（边缘网关/模拟器 → 平台）

```json
{
  "msg_id": "c9d3e2f4",
  "device_id": "CAM001",
  "ts": 1760000100000,
  "event_type": "huddle",
  "confidence": 0.87,
  "bbox": [120, 88, 460, 380],
  "extra": {"animal_count_est": 14}
}
```

| 字段 | 说明 |
|------|------|
| event_type | 枚举（V1.0 三物种共用）：`huddle`扎堆 / `water`圈舍积水 / `cough`咳嗽 / `lethargy`精神萎靡 / `death`死亡牲畜 |
| confidence | 0~1，平台侧低于 0.5 丢弃，0.5~0.7 生成 low，≥0.7 生成 mid 告警；**death 事件例外：confidence ≥0.5 即生成 high**（死亡须人工立即核实，F09 待确认①已采纳） |
| bbox | 可选，像素坐标 [x1,y1,x2,y2]，V1.0 平台不展示，V1.1 截图用 |
| extra | 可选扩展 |

**边界约定**

- 只传结构化事件，**不上传视频流**；视频预览走 RTSP → mediamtx 独立链路，与本协议解耦
- 事件时间以设备 `ts` 为准，平台不做时区换算（统一毫秒）
- 前端展示固定文案："视觉识别结果仅作为提示，不作为确诊依据"

## 五、心跳消息（纯心跳场景）

```json
{
  "msg_id": "a1b2c3d4",
  "device_id": "DEV001",
  "ts": 1760000060000,
  "uptime_s": 86400,
  "rssi": -58
}
```

- `uptime_s`：设备运行秒数；`rssi`：信号强度（dBm，可空）——用于 V1.1 网络质量诊断
- 平台收到 data 或 heartbeat 均刷新 `device:hb:{device_id}`

## 六、模拟器规格（simulator/sensor_sim.py、vision_sim.py）

模拟器 = "用 Python 假装的 STM32 节点"，本节为开发契约。

### 6.1 能力要求

| 能力 | 规格 |
|------|------|
| 参数化 | `--farm --pen --device_id --interval --metrics` 启动参数；支持一进程模拟多设备 |
| 正常模式 | 按 interval 发标准 payload，数值在阈值内随机波动（温度日周期曲线更佳） |
| 异常注入（核心） | `--inject overshoot:metric=temperature,duration=180s`（持续超标）· `--inject spike`（单次抖动，验防抖）· `--inject heartbeat_off`（停心跳，验离线）· `--inject out_of_order`（乱序补发）· `--inject bad_payload`（缺字段/类型错，验消费者健壮性） |
| 视觉模式 | `--mode vision --event huddle --confidence 0.87` 按 event_type 发第四节 payload |
| 幂等重发 | `--inject duplicate`（同 msg_id 重发，验 QoS1 去重） |

### 6.2 验收用例（与测试计划 2.5 节对应）

| 模拟器操作 | 平台预期 |
|------------|----------|
| 连续 3 条超标 | 1 条 sensor 告警 |
| 单条超标后恢复 | 无告警 |
| 停心跳 >5 分钟 | device_offline 告警 |
| 乱序 10 条 | sensor_data 按 collect_time 正确排序 |
| bad_payload | 丢弃+日志，消费者不崩 |
| duplicate | 不产生重复数据/告警 |

## 七、真实硬件接入切换清单（V1.1）

| 步骤 | 动作 | 平台改动 |
|------|------|----------|
| 1 | 设备管理页注册真实设备（真实 device_sn、mqtt_topic） | 无代码改动；**响应额外返回一次性 `device_secret`**（C-24），贴到设备上即可走 HTTP `X-Device-Key` 上报 |
| 2 | STM32 按本协议实现采集/滤波/上报/心跳 | 无 |
| 3 | EMQX 开启设备认证与 ACL（每设备限自己的 topic） | 配置级。注意：HTTP 上行通道的设备密钥已实装，MQTT 通道仍需这一步 + 消费者代码（docs/08 C-24 剩余项） |
| 4 | RTSP 摄像头：填 rtsp_url → mediamtx 转流；边缘网关按第四节发事件 | 无 |
| 5 | 下线对应模拟设备标记 | 无 |

> 协议兼容性承诺：V1.0 平台消费者按本文档实现后，接真实硬件**零代码改动**；如固件开发中发现协议缺陷，先改本文档并升版本，再同步模拟器与平台。
